### Current event architecture and contract

The existing content collector and observer emit category-only structural observations into a bounded content queue. The existing service worker validates each batch, obtains authoritative tab/frame/document context from Chrome, and stores events and a receipt together in `chrome.storage.session`. Browser request/navigation listeners enter the same serialized recorder. Graph and flat exports derive from that recorded stream; graph-derived features are not yet the deployed detection model. Legacy snapshots continue through the existing five-feature ONNX/fallback, assessment, policy, and observation endpoint.

`POST /api/v1/events/batch` accepts **1-100** strict `schema_version: "1.1.0"` events. The schema constrains event/category/trust values, local field/form identifiers, browser document identifiers, timestamps, and origin-only URLs. PostgreSQL identifies events by `(session_id, tab_id, event_seq)`, so retransmitting the same event IDs is idempotent. A successful commit returns `201` with `accepted` and `isStored: true`; a storage failure returns `503`. The worker requires matching persistence acknowledgement before removing pending events. The `accepted` count includes valid retries; it is not a count of newly inserted rows. `POST /api/v1/observations` remains the version 3.0.0 legacy summary contract with strict minimized fields. The compatibility HTTP entry point uses that same observation validator and failure semantics.

Origins retain scheme, hostname, and nondefault port. Paths, queries, fragments, userinfo, raw labels/titles/names, field values, bodies, and headers are not research telemetry. Unknown or opaque origin/document evidence remains unknown. Provenance confidence is a heuristic about observation context, not a calibrated threat probability. A direct form target, request initiator association, and temporal proximity are distinct relationships; a nearby request does not prove that a sensitive value flowed into it. Same-origin path distinctions and server-side forwarding are intentionally unobservable from this minimized stream.

The verification script starts its own loopback FastAPI process on port 8000, an ephemeral fixture server, and a temporary persistent Chromium profile. Port 8000 must be available. Integration checks create controlled database rows; the runtime script retains its evidence rows and overwrites its existing JSON report. No live malicious site or real credential is needed.

The following ceilings are implementation/test facts, not measured browser capacity results: content buffering holds at most **2,000 events per live document** and counts dropped newest events; recorder history and pending delivery hold **2,000 events each per tab**, with pending overflow dropping oldest records and counting the loss. Receipts are limited to **256 content source streams per tab**; new streams are rejected at capacity rather than silently evicting duplicate protection. One worker-wide queue serializes storage and HTTP, so a slow delivery can delay unrelated tabs. Browser-session storage is not durable across browser shutdown. An unacknowledged content buffer is lost when its document is destroyed; a message promise that never settles can stall that document's queue because it has no independent message timeout. The existing runtime report does not yet contain explicit queue/counter snapshots, so it does not establish browser overflow rates or zero dropped-event counters.

## End-to-end source trace

The existing path is `collector.ts → ArtifactManager → messaging/index.ts → service-worker.ts → runDetectionPipeline → features/extractor.ts → ONNX or fallback → assessThreat → makePolicy → popup + POST /api/v1/observations → ObservationRequest → store_observation → observations`.

Dynamic mutations trigger full recollection. `DynamicDOMObserver.triggerImmediate()` collects once and its installed callback ignores that evidence and collects a second time. No stable event identity survives those snapshots. Orphan inputs are handled only when there are no forms, so a document containing both forms and orphan inputs is incomplete. The manifest lacks M1's `storage`, `webRequest`, `webNavigation`, and `all_frames` setup.

M1's separate path is `content.js → TSFEG_M1 message → service_worker.js → chrome.storage.session → buildGraph/buildFlatControl → POST /v1/events/batch → separate FastAPI/pool → events_sanitized`. Merely loading this extension alongside CAPSTONE would create the duplicate pipeline prohibited by G1.

## Minimal integration plan and milestone gates

1. **M0 — completed audit:** preserve baseline, map all requirements, record failures and executable reproductions. Existing foundation is documented as implemented, with failed acceptance requirements separately marked BLOCKED.
2. **M1 prerequisite repair/verification:** fix F01–F04/F08/F09 in reused code, with one runnable check for each shared failure. Prefer prepare these changes in the canonical project integration work rather than building a new standalone product. Any M1/M2 co-development must explicitly document the dependency: reliable/privacy-safe recorder logic must be repaired while adapting it to the existing collector/worker; no duplicate extension is shipped. Do not mark M2 complete before M1 acceptance evidence exists.
3. **M2 — integrate:** one existing collector/observer, one worker, current inference/policy/UI interfaces, one versioned strict event API in existing FastAPI, one migration to existing PostgreSQL. Keep toy inference identified as prototype. Acknowledge persistence failures honestly. Do not add a second pool/dependency merely because M1's standalone backend uses it.
4. **M3/M4 — runtime and correlation:** persistent Chromium context; exact document/frame IDs; DOM/action/request/redirect/iframe scenarios; worker stop/restart; bounded storage; exact browser event-to-DB joins and privacy canaries. Record what cannot be observed. Only then freeze traces for RQ1.
5. **M5 — RQ1:** predeclare label provenance, group-disjoint split, seeds, metrics, practical-effect/FPR/cost criteria. Compare count-flat, temporal/destination-flat, simple destination rule, and graph-derived representations using the identical immutable event stream and the same model family. Fit preprocessing on training only; use validation for choices. Record per-sample predictions and paired group-aware uncertainty. A result showing benefit only over count-flat does not establish graph-specific benefit.
6. **M6–M8:** contradiction rules, calibrated uncertainty, adaptive acquisition only if prior gates allow. Explicit legitimate exceptions and UNKNOWN identities; unavailable sensors cannot produce invented contradiction confidence.
7. **M9–M17:** broader controlled/provenance corpus, corrected dataset splits, baselines, DL only if justified, export parity, dynamic/adversarial/generalization evaluation, actual enforcement, optional enrichment, measured optimization. Small controlled M3–M5 scenarios are prerequisite test fixtures; M9 is broader corpus expansion, not a reason to run RQ1 without traces.
8. **M18–M20:** final implementation-specific prior-art recheck, evidence freeze, disclosure preparation only after the actual mechanism stabilizes and supporting experiments exist. No current readiness or novelty promotion.

Every transition requires code + tests + evidence + documentation. An incomplete prerequisite is not permission to fabricate an experimental result. This audit does not claim that all later milestones have been completed.
